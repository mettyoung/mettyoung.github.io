Capacity limits, request paths & latency budgets for interviews

1. SQL → NoSQL Decision Table (by QPS)

Type QPS Limit Approach / Recommendation
Write ~10k QPS (conservative) Single primary — Acceptable
Write > 10–20k QPS Prefer NoSQL — KV > Wide Column > Document
sharding SQL is complex
Read ~100k QPS 3–5 read replicas — Acceptable
Read > 1M QPS 15–20+ replicas → Expensive

If you need p99 < 2 ms

Requirement Recommended Solution Why
p99 < 2 ms In-memory KV (Redis family) Most reliable option
Still need durability Redis + async persist / primary DB Keep Redis on the fast path
Rule of thumb: Need consistent p99 < 2–5 ms? → Use in-memory KV (Redis).
Disk-based databases (SQL or most NoSQL) rarely deliver consistent sub-2ms tail latency under real load.

3. System Design Patterns

Diagrams use vertical forks where the path branches. Stacked boxes = multiple instances.
QPS & latency are interview ballparks (order of magnitude).

1. Read-Heavy + Cache

Bitly · Yelp · LeetCode · Distributed Cache · Rate Limiter

Read: 100k–1M+ QPS · Write: 1k–10k QPS · p99: < 20–50 ms (Redis hit)

Client → CDN → LB → API GW → App →
hit Redis
miss DB Replica

2. Fan-out on Write

FB News Feed · Instagram · Notification System · FB Live Comments · News Aggregator

Read: 50k–500k QPS · Write: 5k–50k QPS · p99: 50–150 ms (write) / < 50 ms (read from cache)

Client → LB → API GW → App →
write DB
fan-out Kafka → Workers → Timeline Caches

3. Real-time (WS / Pub-Sub)

WhatsApp · Google Docs · Online Chess · Tinder · Uber · ChatGPT · FB Live Comments

Read/Push: 10k–100k msg/s · Write: 10k–100k msg/s · p99: < 50–100 ms (push)

Client ↔ CDN → LB → API GW → WS / SSE →
live Redis Pub/Sub
persist Kafka

4. Media + Async Processing

Dropbox · YouTube · Instagram · Strava

Upload: 1k–20k QPS · Read (CDN): 100k–1M+ · p99: upload < 200–500 ms · processing async

Client → CDN → LB → API GW → App →
store S3
process Kafka → Media Workers

5. Event / Write Aggregation

Ad Click Aggregator · Metrics Monitoring · Price Tracking · Web Crawler · Job Scheduler

Write/Ingest: 50k–1M+ events/s · Read: 1k–20k QPS · p99: ingest < 50–100 ms · query varies

Client → CDN → LB → API GW → App →
write DB
async Kafka → Aggregators

6. Search-Heavy

FB Post Search · Yelp · News Aggregator · YouTube Top K

Read/Search: 10k–100k QPS · Write/Index: 1k–20k QPS · p99: search 50–200 ms

Client → CDN → LB → API GW → App →
read Elasticsearch
index DB → CDC → ES

7. Contention / Consistency

Ticketmaster · Online Auction · Payment System · Robinhood · Local Delivery

Write: 1k–20k QPS (limited by locks) · Read: 10k–100k QPS · p99: 50–200 ms (hot rows higher)

Client → LB → API GW → App →
sync DB + Lock / Queue
async Kafka → Notify / Analytics

8. Geospatial / Matching

Uber · Tinder · Local Delivery · Strava

Location write: 10k–100k QPS · Match/read: 10k–50k QPS · p99: 50–150 ms

Client → LB → API GW → App → Geo Index → Matching
